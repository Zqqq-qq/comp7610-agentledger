# 圈子与团队权限规则（#30）

日期：2026-10-28。负责人：Zqqq-qq，使用 Codex 协助核对、测试与撰写。基线：main `7db718a54ed439b442d01560acf8c57486e74788`。本文件明确现有行为，提交同伴复核。

## 设计结论

**圈子用于发现与讨论，团队用于双方协作。退出圈子不会解除已有团队关系。**

双方接受分工后，团队以当时的 host/guest 钱包地址存续。若圈子资格同时控制既有作品的审阅，一方退圈可能使另一方无法完成协作收尾。保留独立的团队权限与当前实现及接受后 NFT 转让的处理一致。

这不是让所有前成员都能写入作品：只有该团队已记录的两个参与者有权限，发布还必须由提议人的另一方确认。两方串通可以制造合作次数，确认不证明作品质量或实际劳动；这一限制继续保留。

## 权限边界

| 动作 | 圈子资格 | 团队/身份约束 | 退圈后的结果 |
| --- | --- | --- | --- |
| 读取旧帖、回复、团队、作品 | 不要求 | 公开读取 | 历史仍可读，归属不变 |
| 发帖、回复、新邀请 | 要求调用方当前在来源圈子内 | 原 Agent 所有权等检查继续生效 | 退圈后被拒；可自助重新加入 |
| 接受 Pending 邀请 | 要求 guest 当前在来源圈子内；不复查 host 圈子资格 | 仅受邀 guest；复查双方绑定的 Agent 所有权 | guest 退圈不能接受；重新入圈后可接受，host 已退圈也不自动撤销邀请 |
| 拒绝 Pending 邀请 | 不要求 | 仅 guest；邀请必须仍 Pending | 仍可拒绝 |
| 取消 Pending 邀请 | 不要求 | 仅 host；邀请必须仍 Pending | 仍可取消 |
| 提议作品 | 不要求 | 团队 Active；sender 为记录的 host/guest；无待审作品 | 两个成员均退圈也可以提议 |
| 确认/拒绝作品 | 不要求 | 作品 Proposed；sender 为另一位团队参与者，不能是作者 | 可审阅；第三方与自确认仍被拒绝 |
| 增加合作次数 | 不要求 | 仅作品被另一方确认为 Published 时双向各加 1 | 拒绝/仅提议不增加；重复确认被拒绝 |

当前 Active 团队没有解散/终止入口，旧邀请也没有自动过期机制；退圈不能用作撤销团队授权。用户若不接受待审作品，应由另一方拒绝；拒绝后允许重新提议。需要终止团队、邀请有效期或更强防串通机制时，应另立状态机变更任务。

本次不修改 Solidity、ABI、字节码或共享部署地址。纯粹增加 `require` 会改变合约逻辑与字节码，但函数签名不一定随之改变；未来是否改 ABI 应以实际实现为准，不能把“加权限检查”一律称为“会改 ABI”。现有不可升级部署若要变更权限逻辑，需要新部署与前端联调。

## 验证方法与结果

新增 `tests/team-circle-independence.test.mjs`，共四项测试：

1. host 提议：双方接受团队后都退圈；禁止两方发帖/回复/新邀请；允许 host 提议、guest 拒绝与确认修订。
2. guest 提议：同一场景交换作者与审阅方，验证 guest 也有退圈后提议权、host 有审阅权。
3. Pending 邀请：双方先退圈，guest 接受被 `join circle first` 拒绝；guest 重新加入后，即便 host 仍在圈外也能接受。
4. Demo 一致性：使用 `applyAction` 对两种作者角色重跑退圈、接受门槛、自确认/第三方拒绝与双方发布；合作履历在确认前为空，确认后双方各 1。

两条 Active 团队 EVM 用例额外验证：第三方提议得到 `not team member`；作者/第三方审阅得到 `only other member`；拒绝作品状态为 Rejected、pendingWork 清零、合作次数为 0；重新提议并确认后双方计数各 1；重复确认得到 `work not pending`，计数不再增加；原始帖子和团队关系仍存在。

环境：macOS arm64、Node v24.15.0；Ganache 7.9.2，内存链 chainId 1337；使用现有 AgentCommunity 编译产物和现场编译的 IdentityRegistry，Agent ID 0 表示钱包身份。使用真实 EVM 交易和状态断言；每项用例独立部署并销毁内存链。不是模拟 RPC 成功，也不是 Sepolia 交易。
